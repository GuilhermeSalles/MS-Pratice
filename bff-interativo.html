BFF · Backend For Frontend

A camada que fica entre o app e os microserviços. Um backend feito sob medida pra cada tipo de frontend — que agrega chamadas e devolve tudo pronto.

clica nos frontends do diagrama pra ver o fluxo

O que é, em uma frase

BFF é uma camada de backend dedicada a um tipo de frontend. Em vez de web, mobile e TV conversarem direto com os mesmos microserviços, cada frontend ganha um backend sob medida que agrega, filtra e formata os dados no jeito que aquela tela precisa.

O problema que ele resolve

Uma tela de "detalhe da cobrança" precisa de dados que moram em 3 microserviços diferentes: dados do cliente, situação da dívida e histórico de pagamentos. Sem BFF, o app faria 3 chamadas e juntaria tudo no navegador — lógica de orquestração vazando pro frontend.

Com BFF, o app faz 1 chamada só.

  • O frontend chama GET /cobranca/123 no BFF
  • O BFF chama os 3 microserviços internamente, em paralelo se der
  • O BFF junta tudo num único DTO no formato exato da tela
  • Devolve pronto — o app só renderiza, não orquestra nada

Por que "um por frontend"?

Porque cada cliente tem necessidade diferente — e é aqui que a maioria erra na entrevista:

  • Mobile quer resposta enxuta pra economizar dados e bateria
  • Web pode carregar mais detalhes de uma vez
  • Parceiro/TV tem contrato e segurança próprios

Um BFF por frontend serve cada um sob medida, sem inchar uma API genérica que tenta agradar todo mundo e não agrada ninguém.

Frase pronta pra soltar na técnica

"BFF é uma camada de backend dedicada a cada tipo de cliente. Ela agrega chamadas de vários microserviços e devolve a resposta já no formato ideal pra aquele frontend, evitando que o app precise orquestrar várias chamadas e tratar dados que não usa."

BFF ≠ API Gateway (pegadinha comum)

BFF Conhece a tela. Agrega e formata dados pra um frontend específico. Tem lógica de apresentação.

API Gateway Genérico. Cuida de roteamento, auth, rate limit, TLS pra todo mundo. Não sabe o que a tela precisa.

Na prática coexistem: o Gateway é a porta de entrada, e atrás dele vivem os BFFs.

Como funciona Cada frontend fala só com o seu BFF. Os microserviços de domínio (Clientes, Cobrança, Pagamentos) são compartilhados — o BFF é quem monta a resposta certa pra cada tela. Clica num cliente acima.

O que fica em cada camada

Frontend Só renderiza. Faz 1 chamada e mostra. Zero orquestração.

BFF Agrega N chamadas, trata erro parcial, monta o DTO da tela, cuida de auth do cliente. Lógica de apresentação — nunca regra de negócio de domínio.

Microserviço Dono da regra de negócio e dos dados daquele domínio. Não sabe que existe BFF nem tela.

Regra de ouro

Regra de negócio não mora no BFF. Se você começar a colocar cálculo de juros da dívida no BFF, isso é sinal de que devia estar no microserviço de Cobrança. O BFF orquestra e formata — ele não decide.

Como isso vira código em Spring

Um BFF é, na essência, um controller que chama vários clients e monta um DTO. Simples assim. Segue o esqueleto de um BFF de Cobrança.

1 · O DTO da tela (o que o frontend recebe)

CobrancaDetalheDTO.java
// Formato EXATO que a tela precisa — nem mais, nem menos
public record CobrancaDetalheDTO(
    String nomeCliente,
    String situacao,
    BigDecimal valorAtualizado,
    List<PagamentoResumoDTO> ultimosPagamentos
) {}

2 · Os clients (falam com os microserviços)

ClienteClient.java · Feign
@FeignClient(name = "clientes-service")
public interface ClienteClient {

    @GetMapping("/clientes/{id}")
    ClienteDTO buscarPorId(@PathVariable String id);
}
// idem para CobrancaClient e PagamentoClient

3 · O BFF de verdade — o controller que agrega

CobrancaBffController.java
@RestController
@RequestMapping("/bff/web/cobranca")
@RequiredArgsConstructor
public class CobrancaBffController {

    private final ClienteClient clienteClient;
    private final CobrancaClient cobrancaClient;
    private final PagamentoClient pagamentoClient;

    @GetMapping("/{id}")
    public CobrancaDetalheDTO detalhe(@PathVariable String id) {

        // 1. Agrega — chama os 3 microserviços
        CobrancaDTO cob  = cobrancaClient.buscar(id);
        ClienteDTO cli  = clienteClient.buscarPorId(cob.clienteId());
        List<PagamentoDTO> pags =
            pagamentoClient.ultimos(id, 3);

        // 2. Formata — monta o DTO exato da tela
        return new CobrancaDetalheDTO(
            cli.nome(),
            cob.situacao(),
            cob.valorAtualizado(),
            pags.stream().map(PagamentoResumoDTO::from).toList()
        );
    }
}

Repara no que o BFF faz e no que ele NÃO faz:

  • Faz: agrega 3 chamadas, monta 1 DTO sob medida pra tela web (/bff/web/...)
  • Faz: um BFF mobile teria outra rota e devolveria um DTO mais enxuto
  • Não faz: cálculo de juros, decisão de negociação — isso é do microserviço de Cobrança

Detalhe pra brilhar: chamadas em paralelo

Na entrevista, se perguntarem "e se os 3 microserviços forem lentos?" — a resposta madura é fazer as chamadas independentes em paralelo com CompletableFuture (ou WebClient reativo), em vez de uma esperando a outra. Só cuidado: cliente e cobrança aqui têm dependência (precisa do clienteId), então nem tudo paraleliza.

Armadilhas & o que falam contra BFF

Saber os contras é o que separa "decorei" de "entendi". O entrevistador adora perguntar o lado ruim.

⚠️ Duplicação de código

Se você tem BFF web, mobile e parceiro, muita lógica de chamada se repete. Mitigação: extrair a orquestração comum pra uma lib/módulo compartilhado, deixando no BFF só o que é específico de cada tela.

⚠️ Mais uma coisa pra manter e deployar

Cada BFF é um serviço a mais: deploy, monitoramento, on-call. Trade-off: você troca complexidade no frontend por mais serviços no backend. Vale quando os frontends são realmente diferentes; não vale se você tem um só cliente.

⚠️ Risco de virar "God service"

A tentação de jogar regra de negócio no BFF é enorme. Quando isso acontece, ele incha e vira um monólito disfarçado. Disciplina: BFF orquestra e formata. Regra de domínio fica no microserviço. Sempre.

⚠️ Falha parcial

Se o BFF chama 3 microserviços e 1 cai, o que acontece? Você não pode deixar a tela toda quebrar por causa de um pedaço secundário.

  • Use timeout em cada chamada
  • Use circuit breaker (Resilience4j) pra não travar esperando um serviço morto
  • Degrade com elegância: devolve o essencial e um campo vazio pro que falhou, se a tela permitir
Resposta modelo se perguntarem "quando NÃO usar BFF?"

"Quando existe um só tipo de frontend, o BFF vira overhead — uma API bem modelada resolve. BFF faz sentido quando os clientes têm necessidades divergentes o suficiente pra justificar backends separados; caso contrário, é complexidade sem retorno."
